# DNS : le système de résolution de noms

## Rôle du DNS

Le DNS (Domain Name System) traduit des noms de domaine lisibles par des humains (`otela.ht`) en adresses IP exploitables par les machines. C'est un service critique et souvent invisible : sa panne donne l'impression que « tout Internet est cassé », alors que la connectivité IP brute fonctionne parfaitement. Pour un administrateur système, le DNS est aussi un service interne indispensable : résolution des noms de machines sur le réseau local, intégration avec Active Directory (Partie IV), et souvent première ligne de détection d'une compromission (requêtes DNS vers des domaines malveillants).

## Fonctionnement : la hiérarchie DNS

| Niveau | Exemple | Rôle |
|---|---|---|
| Racine | `.` | Point d'entrée, connaît les serveurs de chaque TLD |
| TLD (domaine de premier niveau) | `.ht`, `.com`, `.org` | Connaît les serveurs faisant autorité pour chaque domaine enregistré |
| Domaine faisant autorité | `otela.ht` | Détient les enregistrements réels du domaine |
| Sous-domaine | `app.otela.ht` | Peut être délégué à un autre serveur faisant autorité |

### Types d'enregistrements courants

| Type | Rôle | Exemple |
|---|---|---|
| A | Nom vers adresse IPv4 | `app.otela.ht → 203.0.113.10` |
| AAAA | Nom vers adresse IPv6 | `app.otela.ht → 2001:db8::10` |
| CNAME | Alias vers un autre nom | `www.otela.ht → otela.ht` |
| MX | Serveur de messagerie du domaine, avec priorité | `otela.ht → mail.otela.ht (priorité 10)` |
| TXT | Texte libre, souvent utilisé pour la validation (SPF, DKIM) | `v=spf1 include:_spf.google.com ~all` |
| NS | Serveurs faisant autorité pour le domaine | `otela.ht → ns1.hebergeur.ht` |
| PTR | Résolution inverse, IP vers nom | `10.113.0.203.in-addr.arpa → app.otela.ht` |
| SRV | Localisation d'un service (port et hôte) | Utilisé notamment par Active Directory (Partie IV) |

<div class="encadre info">
<span class="encadre-titre">ℹ️ À savoir</span>
La résolution DNS est massivement mise en cache à chaque étape (résolveur du poste client, résolveur local de l'entreprise, résolveur du fournisseur d'accès) pour limiter la charge sur les serveurs faisant autorité. Le TTL (Time To Live) de chaque enregistrement détermine sa durée de cache : un TTL bas (300 s) permet une propagation rapide des changements mais augmente la charge de requêtes ; un TTL élevé (86400 s) réduit la charge mais ralentit la propagation d'un changement.
</div>

## Prérequis

- Un plan d'adressage déjà en place (Chapitre 8), pour associer noms et IP de façon cohérente
- Une décision sur l'hébergement du DNS interne : intégré à Active Directory (Partie IV), ou serveur DNS dédié (BIND, Windows DNS, dnsmasq)
- Une convention de nommage interne (par exemple `serveur.interne.entreprise.local`)

## Mise en place d'un service DNS interne

1. **Choisir le serveur DNS** — Windows DNS (si Active Directory déjà déployé), BIND9 (Linux, référence historique), ou Unbound/dnsmasq pour un usage plus léger.
2. **Configurer les zones** — Une zone directe (nom → IP) et, recommandé, une zone inverse (IP → nom) pour le diagnostic.
3. **Créer les enregistrements des serveurs internes critiques** — Chaque serveur avec un nom stable, jamais uniquement une IP mémorisée.
4. **Configurer la redirection (forwarding) vers des résolveurs externes** — Pour les requêtes hors du domaine interne (Internet public).
5. **Sécuriser les transferts de zone** — Restreindre quels serveurs peuvent répliquer la zone (voir sécurité ci-dessous).

## Configuration : exemples de commandes

```
# Linux — interroger un enregistrement DNS
dig otela.ht A
dig otela.ht MX
nslookup otela.ht

# Linux — configuration BIND9, extrait de zone
$TTL 3600
@   IN  SOA  ns1.otela.ht. admin.otela.ht. (2026072301 3600 900 604800 3600)
    IN  NS   ns1.otela.ht.
app IN  A    203.0.113.10
mail IN A    203.0.113.20
@   IN  MX 10 mail.otela.ht.

# Windows PowerShell — interroger le DNS
Resolve-DnsName otela.ht -Type A

# Windows Server — créer un enregistrement A via DNS Manager en CLI
Add-DnsServerResourceRecordA -Name "app" -ZoneName "otela.local" -IPv4Address "192.168.20.10"

# Windows — vider le cache DNS local
ipconfig /flushdns
```

## Administration courante

- Surveiller les journaux de requêtes DNS pour détecter des domaines anormaux (indicateur précoce de compromission, Partie XI)
- Auditer périodiquement les enregistrements DNS publics contre l'inventaire réel des services exposés
- Vérifier la cohérence entre zone directe et zone inverse après chaque changement

## Bonnes pratiques

<div class="encadre astuce">
<span class="encadre-titre">💡 À appliquer systématiquement</span>

- Toujours désigner un serveur par son nom DNS dans la documentation et la configuration applicative, jamais par IP brute mémorisée
- Ajuster le TTL en fonction du contexte : abaisser temporairement le TTL avant une migration planifiée, pour accélérer la bascule
- Configurer au minimum deux serveurs DNS internes redondants (Partie IX, haute disponibilité)
- Mettre en place SPF, DKIM et DMARC (enregistrements TXT) pour tout domaine envoyant des emails, réduisant le risque d'usurpation (Partie XI)
</div>

## Erreurs courantes

<div class="encadre attention">
<span class="encadre-titre">⚠️ À éviter</span>

- Laisser les transferts de zone ouverts à n'importe quel serveur (AXFR non restreint), exposant la totalité de la structure réseau interne à un attaquant
- Oublier de mettre à jour un enregistrement DNS après la migration d'un serveur, provoquant des pannes intermittentes selon le cache client
- Configurer un TTL très bas en permanence sans raison, augmentant inutilement la charge sur les serveurs faisant autorité
- Confondre propagation DNS et erreur de configuration : un changement DNS peut mettre jusqu'à la valeur du TTL précédent à se propager partout, ce n'est pas nécessairement un bug
</div>

## Dépannage

| Symptôme | Cause probable | Vérification |
|---|---|---|
| Le nom ne résout pas du tout | Enregistrement absent ou zone mal configurée | `dig` directement contre le serveur faisant autorité |
| La résolution renvoie une ancienne adresse IP | Cache local ou intermédiaire encore valide (TTL) | `ipconfig /flushdns`, attendre l'expiration du TTL |
| La résolution fonctionne en interne mais pas depuis Internet | Zone publique non mise à jour, ou split-DNS mal configuré | Vérifier séparément le DNS interne et le DNS public faisant autorité |

## Recommandations de sécurité

<div class="encadre securite">
<span class="encadre-titre">🔒 Sécurité</span>
Restreindre les transferts de zone (AXFR) aux seuls serveurs secondaires légitimes est une mesure de sécurité de base trop souvent négligée. Envisager DNSSEC pour signer cryptographiquement les enregistrements d'un domaine public sensible, contre les attaques d'empoisonnement de cache. En interne, surveiller les requêtes DNS sortantes reste l'un des moyens les plus efficaces de détecter un poste compromis communiquant avec une infrastructure de commande et contrôle (Partie XI, SIEM).
</div>

## Résumé du chapitre

- Le DNS traduit les noms de domaine en adresses IP via une hiérarchie de serveurs faisant autorité.
- Le TTL détermine la durée de mise en cache de chaque enregistrement, à ajuster selon le contexte (migration à venir ou stabilité).
- Restreindre les transferts de zone et surveiller les requêtes sortantes sont deux mesures de sécurité de base.
- SPF, DKIM et DMARC sont indispensables pour tout domaine envoyant des emails légitimement.
